This page gives you the mental model for working in the current ZGI open-source stack.

## 1. Product shell

`zgi-pre` is the product shell repository.

That means it owns integration, not all business logic. It is the place where we define how the stack boots, how the services connect, and how contributors can start the product locally.

## 2. Submodule-first services

Each major service keeps its own repository, history, and lifecycle.

- `api/`
- `web/`
- `sandbox/`
- `plugin-runner/`

This lets each service evolve independently while still being assembled into one local product experience.

## 3. Root-level orchestration

The root repository is where we coordinate:

- Docker Compose generation
- env bootstrap and sync helpers
- top-level scripts
- GitHub templates and workflows
- submodule pointer updates

If a change is about product integration, it probably belongs here.

## 4. Service-level ownership

If a change is about application behavior, it usually belongs in the service repository itself.

Examples:

- API logic belongs in `api/`
- frontend UI belongs in `web/`
- sandbox runtime behavior belongs in `sandbox/`
- plugin execution flow belongs in `plugin-runner/`

## 5. Bootstrap, not manual setup

The current root startup flow is designed to reduce fragile manual setup.

Instead of asking contributors to hand-copy every env file and remember every command, the bootstrap flow can:

- initialize submodules
- copy missing env templates
- generate the root compose file
- start the stack

This is why `make dev-docker` is the preferred starting point for most contributors.

## 6. Shared infrastructure in product mode

Standalone services may have their own Docker workflows, but the full product stack can reuse shared infrastructure.

For example:

- `sandbox` can run with its own bundled dependencies when started alone
- in `zgi-pre`, `sandbox` reuses the shared root Postgres and Redis

This keeps standalone workflows simple without duplicating infrastructure in the full local stack.

## 7. China-aware builds

Some services support mirror-aware Docker builds for China mainland networks.

At the root level, the current entry point is:

```bash
./dev/start-docker --china
```

The goal is to improve build reliability without permanently rewriting tracked templates.

## 8. Two-layer commit model

When you change code in a submodule, there are usually two commits involved:

1. A commit in the service repository
2. A commit in `zgi-pre` updating the submodule pointer

That is normal for this architecture.

## 9. Documentation scope

The docs site should start by explaining the product shell and the local stack, not by pretending `zgi-pre` is the full implementation repository.

That is why the current onboarding docs focus on:

- what ZGI is
- how to start the stack
- how to think about the repository structure
