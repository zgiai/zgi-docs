# What Is ZGI

ZGI is an open-source AI product stack organized around a top-level integration repository called `zgi-pre`.

`zgi-pre` is not the place where all business logic lives. It is the product shell that brings the stack together for local development, Docker startup, release coordination, and top-level repository management.

## One-sentence definition

ZGI is a product shell for composing the open-source ZGI services into one local stack, with consistent startup workflows, shared infrastructure, and clear repository boundaries.

> ZGI is not trying to collapse every service into one giant repository. It keeps service code independent while giving contributors a single place to boot and integrate the whole stack.

## What `zgi-pre` owns

At the root level, `zgi-pre` is responsible for:

- Docker startup and compose generation
- local bootstrap scripts under `dev/`
- top-level metadata such as GitHub workflows and templates
- release integration across repositories
- English and localized repository README files

## What lives in submodules

The application code stays in dedicated repositories that are pulled in as git submodules:

- `api/` for the backend service
- `web/` for the frontend
- `sandbox/` for code execution isolation
- `plugin-runner/` for plugin execution

This keeps service ownership clean while still allowing us to boot everything together from the root repository.

## Why this structure exists

Most teams hit the same problems when they open-source a multi-service AI product:

1. The real code lives in different repositories.
2. Local startup requires too many manual steps.
3. Docker assets drift from source development workflows.
4. Contributors do not know which repository should own a change.

`zgi-pre` exists to solve those integration problems without forcing every service into a monorepo.

## What this means in practice

When you work in `zgi-pre`, you are usually doing one of these things:

- booting the full local stack
- updating top-level Docker assets
- coordinating env templates and startup scripts
- updating submodule pointers after a service change
- working on contributor-facing docs and repository metadata

If the change is service business logic, it usually belongs in the relevant submodule first.
