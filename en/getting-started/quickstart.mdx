# Quick Start

This guide helps you boot the current `zgi-pre` stack quickly and safely.

## Prerequisites

Before you start, make sure you have:

- Git
- Docker Desktop or a compatible Docker runtime
- Make

## Clone with submodules

Use recursive clone so all service repositories are available immediately:

```bash
git clone --recurse-submodules <repo-url>
cd zgi-pre
```

If you already cloned the repository earlier:

```bash
git submodule update --init --recursive
```

## Start the full local stack

The recommended entry point is:

```bash
make dev-docker
```

On first run, the root bootstrap flow will:

- initialize missing submodules
- copy missing env templates into the right service directories
- regenerate the root Docker Compose file
- boot the local stack

## China mainland build mirrors

If image builds are slow or flaky on mainland networks, use:

```bash
./dev/start-docker --china
```

This mode applies mirror-friendly build settings for the current run without rewriting tracked templates.

## Useful follow-up commands

Check local env drift without overwriting anything:

```bash
make env-check
```

Append only missing template keys while keeping existing values:

```bash
make env-sync
```

Run source development for backend and frontend while keeping shared middleware in Docker:

```bash
make setup
make dev-docker
make dev-api
make dev-web
```

## Default local endpoints

Common local endpoints in the current stack:

- Web: `http://localhost:13000`
- API: `http://localhost:2678`
- Weaviate: `http://localhost:18080`
- Sandbox: `http://localhost:18194`
- Plugin Runner: `http://localhost:15000`

Some host ports can be changed in `docker/.env` if they collide with other local services.

## What happens with infrastructure

In the full `zgi-pre` product stack:

- `postgres` is shared across the stack
- `redis` is shared across the stack
- `sandbox` reuses the shared Postgres and Redis instead of starting dedicated copies

This gives us one coherent local environment while still allowing services like `sandbox` and `plugin-runner` to keep standalone startup paths in their own repositories.

## When you should work in submodules

Use `zgi-pre` to boot and integrate the stack.

Use individual service repositories when you need to change:

- backend behavior in `api/`
- frontend behavior in `web/`
- sandbox runtime behavior in `sandbox/`
- plugin execution behavior in `plugin-runner/`

If you change a submodule, the normal workflow is:

1. Commit in the submodule repository.
2. Commit the updated submodule pointer in `zgi-pre`.
