# 关键概念

这页帮助你理解 ZGI 当前的仓库组织方式。先弄清这些概念，再看启动脚本、Docker 编排和子仓库协作，会少走很多弯路。

## 1. 顶层集成仓库

`zgi-pre` 是 ZGI 的顶层集成仓库。

它的重点是集成，不是承载全部业务代码。它负责定义整套产品如何启动、服务之间如何连接，以及贡献者如何在本地拉起完整环境。

## 2. 服务代码保留在独立仓库

主要服务仍然保持独立仓库：

- `api/`
- `web/`
- `sandbox/`
- `plugin-runner/`

这些仓库各自保留提交历史、发布节奏和维护边界。`zgi-pre` 通过子模块引用它们，并把它们组合成一套可以启动和联调的本地产品环境。

## 3. 顶层编排

顶层仓库主要协调这些事情：

- Docker Compose 生成
- 环境变量模板检查和同步
- 顶层开发脚本
- GitHub 模板和工作流
- 子模块指针更新

如果改动属于“产品级集成”，大概率就该落在这里。

## 4. 服务级归属

如果改动的是应用行为，通常应该放回服务仓库本身。

例如：

- API 行为放在 `api/`
- 前端页面和交互放在 `web/`
- 沙箱执行逻辑放在 `sandbox/`
- 插件执行链路放在 `plugin-runner/`

## 5. 优先使用启动脚本，而不是手工初始化

当前顶层启动流程会尽量减少脆弱的手工步骤。

它会尽量自动完成：

- 子模块初始化
- 环境变量模板补齐
- Docker Compose 文件生成
- 本地栈启动

这也是为什么大多数贡献者都应该先从 `make dev-docker` 开始，而不是自己记一长串启动顺序。

## 6. 完整产品模式下的共享基础设施

单服务可以保留自己的 Docker 启动方式，但完整产品栈可以共享基础设施。

比如：

- `sandbox` 单独运行时可以使用自己的依赖组合
- 在 `zgi-pre` 中运行时，`sandbox` 复用顶层共享的 PostgreSQL 和 Redis

这样既保留独立性，也避免整栈联调时重复起太多中间件。

## 7. 中国网络友好的构建模式

部分服务已经支持面向中国大陆网络环境的 Docker 构建参数。

顶层统一入口是：

```bash
./dev/start-docker --china
```

目标是提升镜像构建成功率，同时不把镜像源配置硬编码进仓库默认模板。

## 8. 两层提交模型

当你修改子模块里的代码时，通常会有两层提交：

1. 子仓库自己的提交
2. `zgi-pre` 中更新子模块指针的提交

这不是额外负担，而是当前仓库结构的正常协作方式。

## 9. 文档应该先讲什么

当前文档站的入门部分，应该先讲清楚：

- ZGI 是什么
- `zgi-pre` 到底是什么仓库
- 如何把本地栈拉起来
- 如何理解顶层仓库与子模块的边界

而不是一开始就假设读者面对的是单体应用仓库。
